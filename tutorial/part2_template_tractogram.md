# PART 2: GENERATION OF WITHIN-SUBJECT TEMPLATES, FIXELS AND TRACTOGRAPHY

One of the key aspects of the presented robust longitudinal quantitative
tractography framework is to unify independent reconstruction steps
where possible, requiring the transformation of session data into a
common image processing space. Since asymmetric image processing has the
risk of biasing results (e.g., transforming one timepoint to the other),
it is common practice to perform any such unified steps in the space of
an unbiased within-subject template. The following steps will outline
how to construct unbiased FOD and T1-weighted within-subject templates
and use this information to derive a tractogram in these templates, as
well as a common brain parcellation that is later used for structural
connectome construction.

> [!NOTE]
> The following steps assume that the primary outcome of the intended
> analysis is the robust longitudinal quantification of white matter
> connectivity. However, if longitudinal grey matter measurements are also
> of interest to the analysis, note that other software packages also
> provide robust longitudinal grey matter reconstruction pipelines that
> similarly operate in an unbiased within-subject template space. This
> similarity can be leveraged through the **integration of longitudinal
> grey and white matter processing** streams; the relevant processing
> steps for such analyses are provided in the Appendix and are intended to
> replace the upcoming steps 2.1 (construction of within-subject
> templates) and 2.2.1 (reconstruction of the T1-weighted template).

## 2.1 Generate unbiased FOD and T1-weighted within-subject templates 

**\[pipeline-specific processing\]**

To build an unbiased within-subject template, we can leverage multiple
contrasts from different modalities. To do this, put all session ODF
images, T1-weighted images (and others if wanted), as well as a set of
corresponding mask images into separate folders (using the same
prefixes):

```bash
mkdir -p template/fod_input

mkdir template/gm_odf_input

mkdir template/csf_odf_input

mkdir template/t1w_input

mkdir template/mask_input
```

Symbolic link all session ODF images (and masks) into the input folders:

```bash
for_each tp* : ln -sr \
  IN/wmfod_norm.mif \
  template/fod_input/PRE.mif

for_each tp* : ln -sr \
  IN/gm_norm.mif \
  template/gm_odf_input/PRE.mif

for_each tp* : ln -sr \
  IN/csf_norm.mif \
  template/csf_odf_input/PRE.mif

for_each tp* : ln -sr \
  IN/dwi_mask_upsampled.mif \
  template/mask_input/PRE.mif
```

To avoid that higher intensity ranges dominate the cost during upcoming
image registration, scale all T1-weighted images to the intensity ranges of the ODFs:

```bash
for_each tp* : sh -c '
  mrconvert IN/wmfod_norm.mif IN/tmp_wm.mif -coord 3 0
  mrcalc IN/tmp_wm.mif IN/gm_norm.mif -add IN/tmp_wm_gm.mif
  mrcalc IN/tmp_wm_gm.mif IN/csf_norm.mif -add IN/tmp_all.mif

  mrhistmatch linear \
    IN/T1w_norm_Warped.nii.gz \
    IN/tmp_all.mif \
    template/t1w_input/PRE.mif

  rm IN/tmp* '
```

For the generation of an unbiased within-subject template, it is
typically sufficient to rely on *rigid* registration, as long as there
are no relevant morphological differences expected between sessions.
However, if relevant morphological differences are expected (e.g.,
pronounced atrophy), non-linear registration is recommended.

For rigid template construction, run the template building script as
follows:

```bash
population_template \
  template/t1w_input template/t1w_template.nii.gz \
  template/fod_input template/fod_template.mif \
  template/gm_odf_input template/gm_template.mif \
  template/csf_odf_input template/csf_template.mif \
  -mask_dir template/mask_input -template_mask template/mask_template.mif \
  -linear_transformations_dir template/transforms/ \
  -type rigid \
  -voxel_size 1.25 \
  -mc_weight_rigid 1,1,0.5,0.0001
```

For non-linear template construction, run the template building script
as follows:

```bash
population_template \
  template/t1w_input template/t1w_template.nii.gz \
  template/fod_input template/fod_template.mif \
  template/gm_odf_input template/gm_template.mif \
  template/csf_odf_input template/csf_template.mif \
  -mask_dir template/mask_input -template_mask template/mask_template.mif \
  -warp_dir template/transforms/ \
  -type rigid_affine_nonlinear \
  -voxel_size 1.25 \
  -mc_weight_rigid 1,1,0.5,0.0001 \
  -mc_weight_affine 1,1,0.5,0.0001 \
  -mc_weight_nl 1,1,0.5,0.0001
```

The voxel size is typically set to match the voxel size of the input FOD
images (which, in this pipeline, would typically be the resolution the
preprocessed data was upsampled to, earlier on in the pipeline).


> [!TIP]
> The ```T1w_norm_Warped.nii.gz``` files here used as T1-weighted input were
> automatically generated by ANTs during registration across modalities
> within sessions. This means, they are spatially aligned with the DWI
> data but have been resampled to their resolution, which typically is
> lower than the native resolution of T1-weighted images. To generate
> *full-resolution* within-subject templates, one can also apply the
> derived transform manually to the T1-weighted image *without*
> resampling, resample ODF images onto this higher-resolution grid, and
> provide those images as input to the command. Full-resolution non-linear
> registration should be considered if large morphological changes are
> expected between sessions, or if registration quality is found to be
> insufficient.

> [!NOTE]
> Here coregistration weights of 1,1,0.5,0.0001 are specified, defining
> the weighted contribution of each image contrast to the registration
> cost (order of numbers corresponds to order of the input contrasts). In
> this configuration, registration is primarily driven by the T1-weighted
> images and WM ODFs, with a moderate contribution from GM ODFs. The
> reasoning of this specification is that T1-weighted contrasts, and to a
> lesser extent also GM ODFs, provide meaningful information for the
> alignment of cortical and subcortical structures, whereas WM ODFs
> provide meaningful information for the alignment of the deep white
> matter. CSF ODFs on the other hand contain little spatially specific
> information and were therefore strongly downregulated in their
> contribution to the registration cost (nonetheless, they were included
> to derive an output CSF template). Note, however, that these parameters
> were not chosen based on an exhaustive exploration of the parameter
> space, and should be seen only as an **educated guess** of what could be
> a sensible specification of multi-contrast registration weights.
> Inspection of registration quality is strongly recommended.

If non-linear registration was chosen, population template will have
exported the relevant 5D warps, containing linear transforms, warps and
their inverses that map each image to a midway space. To convert these
into deformation fields for further use run:

```bash
for_each tp* : warpconvert \
  template/transforms/IN.mif \
  warpfull2deformation \
  template/transforms/IN_subject2template_deformation.mif \
  -from 1 \
  -template template/fod_template.mif
```

> [!WARNING]
> It is absolutely **crucial** to check at this stage that the resulting
> template mask includes *all* regions of the brain that are intended to
> be analysed. If this is not the case, the cause will be either an
> individual session mask which did not include a certain region, or the
> template building process having gone wrong. It is advised to **go
> back** to these steps, and identify and resolve the cause of the problem
> before continuing any further.

> [!NOTE]
> It is possible at this stage to edit the template mask and remove
> certain regions that are either not part of the brain (though these are
> unlikely to survive the intersection step to begin with, as they would
> have to be present in *all* session masks for this to happen), or
> otherwise not of interest. However, **do not add regions to the
> mask** at this stage. If there is a genuine need to do this, go back to
> the relevant steps which caused the exclusion of these regions to begin
> with (see also the above warning).


## 2.2 Derivation of relevant T1-weighted outputs

To construct structural connectomes, we will use anatomical information
derived from T1-weighted images, specifically, tissue segmentations

and a cortical parcellation.

### 2.2.1 Reconstruction of the T1-weighted within-subject template 

**\[pipeline-specific processing\]**

To obtain tissue segmentations and a cortical parcellation in the
unbiased template space, we leverage outputs generated by FreeSurfer's
*recon-all* processing stream.

To reconstruct the T1-weighted within-subject template using recon-all
run:

```bash
recon-all \
  -i template/t1w_template.nii.gz \
  -sd template \
  -s recon_template \
  -all \
  -parallel \
  -openmp 8
```

> [!TIP]
> The execution of recon-all provided here is optimised for accelerated
> extraction of the required outputs from a *single subject*. Both hemispheres
> are processed in parallel, with computationally intensive steps that support 
> multithreading are executed using eight cores. When processing multiple T1-weighted 
> within-subject templates across a cohort, however, efficiency can be significantly improved by 
> parallelising single-threaded recon-all runs at the cohort level (see [multi-threaded use of ```for_each```](https://mrtrix.readthedocs.io/en/dev/reference/commands/for_each.html) for more information).

> [!NOTE]
> In case of non-ideal surface reconstructions, consider construction of a
> *full-resolution* T1-weighted template which is then run through
> recon-all. Also remember to cite the relevant articles of external
> software packages with respect to the specific algorithms (FreeSurfer).

### 2.2.2 Segmentation of different tissue types

**\[pipeline-specific processing\]**

For downstream fibre-tracking and tractogram density optimisation,
tissue segmentations are used as anatomical priors. They can be
generated using the following command:

```bash
5ttgen hsvs \
  template/recon_template \
  template/5tt.mif \
  -template template/mask_template.mif
```

This will generate a five-tissue-type segmentation image from
FreeSurfer's cortical surface reconstruction; subcortical structures are
segmented through FSL's ```FIRST``` algorithm.

> [!NOTE]
> Before running ```5ttgen```, we strongly recommend users to install the ```ACPC
> Detect``` software package, as it allows for improved detection of the
> anterior and posterior commissure. Absence from these structures in the
> tissue segmentation means that they will not be reconstructed during
> downstream fibre-tracking.

### 2.2.3 Derivation of a cortical and subcortical brain parcellation

**\[pipeline-specific processing\]**

Since we want to quantify structural connection density between brain
regions, we also need to define regions of interest. While many
different labelling strategies are available, we here will use
FreeSurfer's default Desikan Killiany parcellation. The relevant
FreeSurfer output can be converted into a parcellation image with nodes
incrementing from one:

```bash
labelconvert \
  template/recon_template/mri/aparc+aseg.mgz \
  $FREESURFER_HOME/FreeSurferColorLUT.txt \
  path/to/mrtrix3/share/mrtrix3/labelconvert/fs_default.txt \
  template/nodes.mif
```

> [!NOTE]
> Remember to cite the relevant articles of external software packages
> with respect to the specific algorithms (FreeSurfer, FSL first, ACPC
> Detect).


## 2.3 Fixels and fixel-based quantitative metrics

### 2.3.1 Compute a white matter template analysis fixel mask 

**\[pipeline-specific processing\]**

In this step, we segment fixels from the FOD template. The result is
the *fixel mask* that defines the fixels which will be used for later
quantitative streamline tractography:

```bash
mkdir template/fixels

fod2fixel \
  -mask template/mask_template.mif \
  template/fod_template.mif \
  template/fixels/fixel_mask \
  -maxnum 5 \
  -afd fd.mif
```

> [!NOTE]
> Fixel images, which appear in the pipeline from this step onwards, are
> stored using the [Fixel image (directory)
> format](https://mrtrix.readthedocs.io/en/latest/fixel_based_analysis/fixel_directory_format.html#fixel-format),
> which stores all fixel data for a fixel image in a directory (i.e. a
> folder).

> [!WARNING]
> This step ultimately determines the fixels used for quantitative
> streamline tractography, so it may have a substantial impact on the
> final result. Essentially, it can be detrimental to the result if the
> threshold value (can be manually specified via ```-fmls_peak_value```) is *too
> high* and hence *excludes* genuine white matter fixels. This risk is
> substantially higher in voxels containing crossing fibres (and higher
> the more fibres are crossing in a single voxel). It is still **strongly
> advised** to visualise the output fixel mask
> using [```mrview```](https://mrtrix.readthedocs.io/en/latest/reference/commands/mrview.html#mrview).
> Do this by opening the index.mif found in template/fixels/fixel_mask via
> the *fixel plot tool*. If, with respect to known or normal anatomy,
> fixels are missing (especially paying attention to crossing areas),
> regenerate the mask with a lower value supplied to
> the ```-fmls_peak_value``` option (of course, avoid lowering it *too* much, as
> too many false or noisy fixels may be introduced). For an *adult
> human* brain template, and using an isotropic template voxel size of
> 1.25 mm, it is expected to have several *hundreds of thousands* of
> fixels in the fixel mask (you can check this
> by ```mrinfo -size template/fixels/fixel_mask/directions.mif```, and looking at the
> size of the image along the first dimension).


### 2.3.2 Transform FOD images to template space 

**\[standard processing\]**

Next, we will transform FODs to the unbiased within-subject template.
Dependent on whether templates were generated using rigid or non-linear
registration, we will transform FOD images to template space either
*with* or *without* FOD reorientation.

If rigid registration was used for template construction run:

```bash
for_each tp* : mrtransform \
  IN/wmfod_norm.mif \
  -linear template/transforms/IN.txt \
  -reorient_fod yes \
  IN/fod_in_template_space_REORIENTED.mif \
  -template template/fod_template.mif
```

If non-linear registration was used for template construction run:

```bash
for_each tp* : mrtransform \
  IN/wmfod_norm.mif \
  -warp template/transforms/IN_subject2template_deformation.mif \
  -reorient_fod no \
  IN/fod_in_template_space_NOT_REORIENTED.mif
```

> [!NOTE]
> The reason for performing FOD transformation without reorientation in
> the case of non-linear transforms has to do with risk introducing
> deformations to the FOD shape, which can result in different downstream
> fixel segmentations. To mitigate this problem, fixels are segmented from
> transformed but non-reoriented FODs; reorientation is then performed
> *after* segmentation on fixels.

### 2.3.3 Segment FOD images to estimate fixels and their apparent fibre density 

**\[standard processing\]**

Here we segment each FOD lobe to identify the number and orientation of
fixels in each voxel. The output also contains the apparent fibre
density (AFD) value per fixel (estimated as the FOD lobe integral).

If rigid registration was used run:

```bash
for_each tp* : fod2fixel \
  -mask template/mask_template.mif \
  IN/fod_in_template_space_REORIENTED.mif \
  IN/fixel_in_template_space \
  -maxnum 5 \
  -afd fd.mif
```

If non-linear registration was used run:

```bash
for_each tp* : fod2fixel \
  -mask template/mask_template.mif \
  IN/fod_in_template_space_NOT_REORIENTED.mif \
  IN/fixel_in_template_space_NOT_REORIENTED \
  -maxnum 5 \
  -afd fd.mif
```

The following steps will use the shortened acronym *Fibre Density (FD)*
to refer to the to this metric.

> [!NOTE]
> In this pipeline, we use fibre density measurements that are based on
> the AFD metric; however, conceivably, one could also derive through such
> measurements through alternative diffusion models.

### 2.3.4 Reorient fixels 

**\[standard processing\]**

> [!NOTE]
> This step is **only required if non-linear registration was used**. Skip
> it if rigid registration was performed of within-subject template
> generation.

Here we reorient the fixels of all subjects in template space based on
the previously estimated non-linear transform:

```bash
for_each tp* : fixelreorient \
  IN/fixel_in_template_space_NOT_REORIENTED \
  template/transforms/IN_subject2template_deformation.mif \
  IN/fixel_in_template_space
```

After this step, the ```fixel_in_template_space_NOT_REORIENTED``` folders can
be safely removed.

### 2.3.5 Assign subject fixels to template fixels 

**\[pipeline-specific processing\]**

While each session's data has already been (spatially) transformed to
the common within-subject template space, and also session fixels have
been reoriented accordingly, there is still no specification of which
fixels match (across sessions and template fixels). This step
establishes exactly that, by matching the fixels of each individual
session to the single common set of within-subject template fixels. This
is achieved by, for each fixel in the within-subject template,
identifying the corresponding fixel in the matching voxel of the session
image and assigning the FD value of this corresponding session fixel to
that fixel in template space. If no fixel exists or can be found in a
session that corresponds to a given within-subject template fixel then
it is assigned a value of zero (as the absence of a session fixel at
this stage is most likely due to a very low, or even zero, FD). 

> [!NOTE]
> If the shape of FODs changes markedly between sessions (biological
> change, noise, etc.), fixel segmentations derived from these FODs can
> also differ. If mapping fixels of each session to template fixels only 
> based on directional correspondence, gross differences in fixel segmentations 
> can manifest as spurious change, which can be deleterious to the detection 
> of subtle effects. To mitigate this, we here adopt an [advanced strategy for
> ```fixelcorrespondence```](https://www.researchgate.net/publication/326146373_Mitigating_the_effects_of_imperfect_fixel_correspondence_in_Fixel-Based_Analysis)
> that also considers the preservation of fibre volume during the mapping
> process. The relevant code to run this advanced correspondence strategy
> is [available through the MRtrix3 GitHub repository](https://github.com/MRtrix3/mrtrix3/tree/fixelcorrespondence).
> After sucessful compilation of the command, replace ```path/to/installation``` in the upcoming code section with the relevant path on your system.

Advanced fixel correspondence, which accounts not only for directional similarity 
but also for preservation of fibre volume, is performed in two stages.

First, we estimate fixel-wise mappings from session space to template space:

```bash
mkdir template/fixels/mappings

for_each tp* : path/to/installation/fixelcorrespondence \
  IN/fixel_in_template_space/fd.mif \
  template/fixels/fixel_mask/fd.mif \
  template/fixels/mappings/IN_to_template \
  -algorithm in2023
```

> [!NOTE]
> This mapping step can be computationally intensive. If it’s taking longer than expected, 
> consider reducing the maximum number of fixels during segmentation of the fixel mask and session fixels (```fod2fixel [...] -maxnum N```)

Then, we apply these mappings to the session-wise FD images to obtain corresponding FD 
values for the template fixels:

```bash
mkdir template/fixels/metrics
cp template/fixels/fixel_mask/index.mif template/fixels/fixel_mask/directions.mif template/fixels/metrics/

for_each tp* : path/to/installation/fixel2fixel \
  IN/fixel_in_template_space/fd.mif \
  template/fixels/mappings/IN_to_template \
  sum template/fixels/metrics \
  fd_IN.mif
```

Note that the output fixel directory ```template/fixels/metrics/``` is the same for
all sessions. This makes sense, since after this operation, there is
only a single remaining set of fixels (i.e. the template fixels), with
corresponding FD values as obtained from each session. This resulting
directory ```template/fixels/metrics/``` now stores these data as timepoint fixel data
files: one for each session, and all with respect to a single set of
corresponding template fixels.


### 2.3.6 Compute the fibre cross-section (FC) metric 

**\[standard processing\]**

> [!NOTE]
> This step is **only required if non-linear registration was used**
> and should be skipped in the case of rigid transforms. This is because
> rigid body transformations per definition preclude any volumetric
> change, so measuring local volume change would be inconsequential.

In certain cases, pathology may impact the cross-sectional size of a
bundle. However, the FD metric as computed above is only sensitive to
the density of intra-axonal space in each voxel, yet not the
cross-sectional size of bundles. Since this is another property that
would factor into a bundle's total intra-axonal space across its full
cross-sectional extent, we here compute a fixel-based metric related to
morphological differences in fibre cross-section (FC), as well as a
combined fixel-based metric that captures both, differences in fibre
density and cross-section (FDC;
[\[Raffelt2017\]](https://mrtrix.readthedocs.io/en/latest/reference/references.html#raffelt2017) for
more information).

The FC metric is computed entirely from the warps generated during
registration, measuring the volumetric change at each fixel with respect to its
orientation:

```bash
for_each tp* : warp2metric \
  template/transforms/IN_subject2template_deformation.mif \
  -fc \
  template/fixels/fixel_mask \
  template/fixels/metrics \
  fc_IN.mif
```

> [!NOTE]
> The FC as calculated here is a *relative* metric, expressing the local
> fixel-wise cross-sectional size *relative* to the within-subject
> template. While this makes it possible to interpret differences of
> FC *within* a single individual (because only a single unique template
> is used for this subject), the FC values should not be compared across
> different subjects that each have their own within-subject template.
> Reporting absolute quantities of FC, or absolute effect sizes of FC,
> also provides little information; as again, it is only meaningful with
> respect to the template.


### 2.3.7 Compute a combined measure of fibre density and cross-section (FDC)

**\[standard processing\]**

> [!NOTE]
> This step is **only required if non-linear registration** **was used**
> and should be skipped in the case of rigid transforms.

The total capacity of a fibre bundle to carry information, is modulated
both by the local fibre density at the voxel (fixel) level, as well as
its cross-sectional size. Here we compute a combined metric, which
factors in the effects of both FD and FC, resulting in a fibre density
and cross-section (FDC) metric:

```bash
for_each tp* : mrcalc \
  template/fixels/metrics/fd_IN.mif \
  template/fixels/metrics/fc_IN.mif \
  -mult \
  template/fixels/metrics/fdc_IN.mif
```

This is also a nice example of how calculations across multiple fixel
data files can be performed. However, note that this is only valid if
these both share the same set of original fixels (in this case, the
template fixel mask).



## 2.4 Perform whole-brain tractography on the within-subject template 

**\[pipeline-specific processing\]**

To generate a whole-brain tractogram with trajectories that are unbiased
in respect to all sessions, tractography is performed on the FOD
within-subject template:

```bash
tckgen \
  -act template/5tt.mif \
  -seed_dynamic template/fod_template.mif \
  -select 10000000 \
  template/fod_template.mif \
  template/tracks_10M.tck \
  -cutoff 0.06
```

> [!WARNING]
> The appropriate FOD amplitude cutoff for FOD template tractography can
> vary considerably between different datasets, as well as different
> versions of *MRtrix3* due to historical software bugs. While the value
> of 0.06 is suggested as a reasonable value for multi-tissue data, it may
> be beneficial to first generate a smaller number of streamlines (e.g.
> 100,000) using this value, and visually confirm that the generated
> streamlines appropriately reconstruct known white matter anatomy, before
> committing to generation of the dense tractogram.
